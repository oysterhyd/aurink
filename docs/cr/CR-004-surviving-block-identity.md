# CR-004 · BlockID 的存活与语法依赖边界

- 提出：BE-1（S3），2026-11-01
- 状态：待 CEO 批复；本提案没有修改任何契约源码。
- 兼容级别：冻结前语义澄清，不增加签名；冻结后改变既有承诺须 CEO 判断是否作为主版本调整。

## 动机与证据

04 §4.2.6 的「未与任何 Change 相交的块保持 ID」对任意 Markdown 编辑不能无条件成立。

[实测] `TestIdentityBoundariesAndGrammar/open-fence-swallow`：在 `a\n\nb\n` 的开头插入 `` ```\n ``，插入点与两个段落的源码区间均不相交，但两个段落都被新的未闭合代码块吞掉。没有两个存活块可承载旧 ID。删除段间空白也可以合并块，插入 Setext 下划线可以改变前一块种类。

[实测] S3 的三组固定种子共 30,000 步中，1,085,936 次「同种类、完整区间映射后仍存活」检查的 ID 全部保持；同时出现 15,975 次源码不相交但块不再具有该完整区间/种类的情况，不能把这些算成身份保存失败或全部忽略而不报告。

引用定义变化还有另一种依赖：[实测] 修改远处的引用定义可以改变原段落的内联语义，但段落 ID 应保持。[源码] 解析器用 `Revision()` 标识内联重建。因此 ID 稳定不能当作内容未变或缓存有效的证明；`DocEvent.Dirty` 必须包含这类引用用户。

## Go diff（提案）

```diff
 // contract/ast.go
-// BlockID 是块的稳定标识：块在编辑中存活时保持不变，用作排版缓存键与视图 Key。
+// BlockID 是块的稳定标识；语法重解析后仍存活的块继承 ID。
+// 源码未与 Change 相交且种类、映射后的完整区间相同的块，必须继承 ID。
+// 对其余候选，种类和映射后的起点相同、旧起点未被删除，且旧 ID 尚未占用时，
+// 按文档顺序继承 ID；
+// 必须先为完整区间相同的存活块保留身份，不能由其他候选抢占。
+// 合并、拆分或被容器吞并而消失的块不保留独立身份；新 ID 永不复用。
+// ID 不表示内容修订；内联依赖改变时须另行失效投影/排版缓存。
 type BlockID uint64
```

建议同步澄清 04 §4.2.6：上述第二类「种类和起点相同」继承仍作为确定性要求，但以前一类存活候选优先、旧起点未被删除、ID 一对一为条件。

映射边界：插入在块起点时，未触及后继块的起点取插入后的偏移；插入在块终点时，原区间终点取插入前的偏移。若语法导致原区间扩张/合并，转入第二类或分配新 ID。空表格单元格可同种类、同区间，须按文档顺序匹配多重候选，禁止重复 ID。

## 影响与过渡

- BE-1 `core/markdown`：先匹配未触及的完整范围，再匹配同种类/起点候选，最后单调分配 ID；单独跟踪语义变化和 Dirty，不以是否换 ID 判断。
- QA：mock 和 contracttest 同时覆盖起点/终点插入、段落打字、块合并/拆分、开放围栏吞并、引用定义失效、同范围空表格单元格及删除后不复用 ID。
- FE-1：消失块的缓存按 ID 移除；存活块仍需处理 Dirty。大纲、导出无需新接口。
- 与 CR-001 的新增空块合并时，空块也须定义确定性的候选顺序与边界 affinity。

[实测] S3 在私有 `engine` 中实行上述匹配规则，没有实现或修改公开 AST。[待验证] 正式 `AST`、`DocEvent.Dirty` 和 FE 缓存接线留待 M0 批复后的任务。
