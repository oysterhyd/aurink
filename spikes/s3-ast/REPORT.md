### 方法与反例

[源码] `document.go` 的 Kind 和块拓扑映射到 contract；`html.go:Line/LineCount` 实际未限制块种类，段落、标题、单元格也可调用。[实测] 全语料确认可用。适配层从返回的源码偏移建立内容行，按真实 CR/LF 定位行边界，生成删除区间；再独立用 `Range - Prefixes - Markers` 重建内容，逐行与 `parser.Lines` 比较。仅用于比较的行尾统一为 LF，每条内容行包括最后一行都补 LF；源字节不变。另有手写 envelope、标记不含祖先引用前缀、相邻空数学块不吞下一开符号的黄金断言。

[实测] CommonMark/GFM #5、#6、#7 等 Tab 例子，删除后的 `foo` 与解析器的 `  foo` 不相等。9 个失败块都在需要部分 Tab 补空格的代码内容中。私有 `contentLine{Source, Padding}` 补回剩余 0..3 个空格后，全语料成立；这是一种修改表示后的可行方案，**没有把它计为当前严格规则的通过**。CR-003 提议为契约增加精确逐行映射。

[源码] [实测] `finalize` 有时把块 End 改成最后内容段的末端，因而不能直接把 parser.Start/End 当作包含所有定界符的完整 Range。原型修复了 ATX 闭合井号、Setext 下划线与数学闭合符的包围区间，围栏行和续行容器前缀分别归入 Markers/Prefixes。首行的祖先标记位于叶子 Range 之前，由祖先拥有。`Content` 是首尾内容的包围区间，多行时仍可包含内部前缀及原始换行，不能当成单一去标记子串。

[待验证] 叶子与祖先标记、块间空白的全文覆盖须结合已有 CR-001 统一设计；本原型没有自行采用其待批复的 Blank/Trailer 类型。

## 3. BlockID 与增量正确性

[实测] 每个种子 10,000 步，固定 seed=1331、20261101、73；在 UTF-8 边界上混合插入/删除/替换，允许拆开 CRLF，片段包含 CJK、emoji、围栏、表格、引用定义、脚注、Tab 和换行。逐步对照新的全量解析：块拓扑、种类、完整范围、Content、Markers、Prefixes、属性、内容行、内联种类/范围/文本/目标/Next 和 HTML；不只是比较 HTML。ID 断言还检查非零、唯一和退役 ID 永不复用。

| 模式 / 种子 | 全量结构与内联等价 | 存活未触及 ID 检查 | 源码不相交但该块消失/重组 | 引用保护全量回退 | 实际 parser.Edit / Front Matter 重解析 |
|---|---:|---:|---:|---:|---:|
| 保护开启 / 1331 | 10,000/10,000 | 335,156/335,156 | 5,065 | 5,897 | 4,053 / 50 |
| 保护开启 / 20261101 | 10,000/10,000 | 374,491/374,491 | 5,372 | 6,591 | 3,405 / 4 |
| 保护开启 / 73 | 10,000/10,000 | 376,289/376,289 | 5,538 | 4,983 | 4,956 / 61 |
| 保护关闭 / 20261101 | 10,000/10,000 | 374,491/374,491 | 5,372 | 0 | 9,971 / 29 |
| 保护关闭 / 73 | 10,000/10,000 | 376,289/376,289 | 5,538 | 0 | 9,935 / 65 |

保护开启共 **12,414 次实际 parser.Edit**，超过一万步；其余明确记录为重解析，不把全量回退称作增量成功。引用保护在此对抗性语料中触发 17,471/30,000 次，约 58.2%；它是保守正确性的代价，不代表普通文档的触发率。两个关闭保护的运行仍保留 Front Matter 重识别，故也不声称每一步都调用 parser.Edit。

[源码] [实测] ID 用单调计数器；先匹配种类与映射后的完整区间，为未触及存活块保留身份；再对旧起点未被删除、种类/映射起点相同的候选继承；最后分配新 ID。同区间空表格单元格用有序候选避免 ID 冲突。单独验证了块前插入、段内打字、删除空白合并、开放围栏吞并与远处引用定义修改。

[实测] 两个未被编辑字节触及的段落可在开头插入开放围栏后同时消失，因此原契约的无条件规则无法满足。CR-004 明确「存活」含义；上表没有把消失的 15,975 次候选悄悄算入成功分母。仅偏移平移保持 ID 也不等于内容缓存有效，引用定义可改变远处内联语义。

### 原始解析器的已知反例

1. **[实测] 缩进代码块错误分裂。** 初始 `"    e\n容\n``\n---|"`，Edit(6,16,"\t")。原始增量结果 3 块、全量 2 块（含根）。种子 1331 首次在 step=1020 发现，同类相邻缩进代码块被错误保留为独立兄弟。`TestParserEditKnownMismatch` 保存最小反例。原型检测相邻同父、非围栏代码块后全量重解析，不用全量 oracle 决定运行时是否回退。
2. **[实测] 引用/脚注缓存失效冲突。** 初始 `"[^x]:[^x]\n\r[\n^x]: 注*"`，先读取 Inlines，再 Edit(16,22,"\t")；缓存内联仍为 Link，而全量结果为 FootnoteRef。`TestParserReferenceInvalidationWitness` 保存反例；不只比较 HTML，因为未引用脚注定义中的内联差异可能被 HTML 导出隐藏。另一次缩减得到 `"[^x]\n[^x]:[^x\r]:a"` 中 Edit(12,12,"中")，说明还需覆盖标签尾部空白。

[源码] `block.go:refsChanged` 用 `"^"+label` 同时表示脚注失效键，而普通引用标签经规范化也能成为同一个键。公开 API 不提供引用环境注入或内联缓存清除。原型遇到带空白的 caret 标签（修改前或后）保守全量重解析。上面的保护频率已披露；单独反例验证两类回退有效，随机序列中代码回退为 0（较宽的引用保护已提前触发）。

[待验证] 两项保护只由这些语料与固定种子支持，不是上游 parser.Edit 无其他缺陷的证明。需要 INT 记录/转交 MyGo 缺陷与最小用例；S3 未改缓存源码、未升级 MyGo，也未将未经批准的补丁加入依赖。

## 4. Front Matter

[实测] 只在启用时、原文第一行恰为 `---` 且有闭合 `---` 或 `...` 行时识别，支持 LF、CRLF、lone CR 和无尾换行的关闭行。未关闭、前置空行、缩进、尾随空格、开关关闭都不剥离。BOM 由文件层处理，带 BOM 的输入在此不识别。内容不要求是有效 YAML，解析错误属于后续元数据层。

[实测] `BlockFrontMatter.Range` 覆盖开闭行及闭合行 EOL，Content 为内部原始 YAML 包围区间；正文 parser 只接收 source[bodyAt:]。块、行、内联和标记偏移整体加 bodyAt，父/Next 索引平移；显式首块编辑和随机编辑后与全量预处理等价。编辑触及 Front Matter 或改变其识别结果时重建 parser，正文内编辑才使用相对偏移的 Edit。

[待验证] Front Matter 的 YAML 字段解释、可视页眉与编辑命令留待 BE-1.7，不在 S3 交付中。

## 5. Escape / Entity 二次扫描

[实测] 仅扫描 parser.Text 的原始范围，生成独立 `contract.InlineEscape`（Open 指向反斜杠）与 `InlineEntity`（Text 为解码值），保留字节范围并重新计算平坦树 Next。使用公开 `parser.Entity`，避免标准库 HTML 解码对无分号/旧实体前缀的宽松行为偏离 Markdown。自造黄金覆盖 CJK 前缀偏移、两反斜杠、非法转义、无效实体、数值 0、多码点实体、嵌套强调、CRLF、表格转义管道。

[源码] [实测] 不扫描 Code/HTML/Math、链接目标以及自动链接子文本；否则 `<https://a/\*>` 会被错误二次解码。Text 合并可能跨过硬换行被移除的尾空格，原型验证解码与 parser.Text 一致并保留相应原始范围。表格的 `\|` 先由解析器处理，普通 Text 扫描可补成 Escape，但代码跨度仍保持 opaque。全语料二次扫描与解析器 Text 内容比较无差异。

## 6. 性能曲线与分片

[实测] `CGO_ENABLED=0 GOMAXPROCS=1`，每个模式 10 次操作、3 轮；下表取**三轮 ns/op 均值的中位数**，不是单击键 p95。输入大小为 UTF-8 字节的二进制单位：100 KiB=102,400、1 MiB=1,048,576、5 MiB=5,242,880。CPU 调频/GC 带来波动，完整范围与 B/op、allocs/op 在原始输出中。

| 文档大小 | 含根块数 | Parser 全量 | Parser 单次中部 Edit | 原型适配全量 | 原型适配 Edit | 闭合分片局部 Edit | 引用定义向全部分片广播 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 100 KiB | 5,308 | 3.21 ms | 0.64 ms | 6.57 ms | 7.40 ms | 0.185 ms | 1.81 ms |
| 1 MiB | 54,371 | 35.03 ms | 15.57 ms | 85.18 ms | 95.94 ms | 0.271 ms | 17.22 ms |
| 5 MiB | 271,847 | 137.42 ms | 54.28 ms | 384.49 ms | 454.33 ms | 0.118 ms | 99.28 ms |

所有全量与 Edit 模式都触发内联解析；适配模式还执行全叶子 Escape/Entity 补全与全局 ID 匹配。文档含标题、两行段落、嵌套引用任务列表、围栏代码、CJK、强调、实体和全局引用定义，块密度较高，不能直接与 P12 的另一份输入横向比较。5 MiB 的 parser Edit 分配约 72.0 MB/op；原型适配 Edit 约 554 MB/op，显示当前每次重建所有 Block/行/内联与匹配表的成本。这里没有把未实现的生产缓存收益写成实测。

[源码] parser.Edit 除了重解析，还复制源字符串、尾块/segments/已解析内联并平移偏移；因此小改动仍有全文 O(n) 工作。原型适配器又重建整份元数据。**[实测] 当前原型不满足 1 MiB 编辑 16 ms 的整条编辑链预算**；原始 parser 本身已接近/超过预算，产品应保留大文件降级，正式适配不能沿用此 eager 路径。

### 分片可行性与限制

- **[实测] 仅局部闭合分片有明显收益。** 每片由完整顶层单元组成，约 16 KiB；单片 Edit 的三组中位数为 0.118–0.271 ms，文档总长度不进入局部解析。该数字没有计入全文字符串复制、偏移索引、统一 AST/ID 更新和分片边界维护，不能当作产品击键延迟。规模相同的局部片在各组间波动来自测量噪声。
- **[实测] 独立解析会丢失引用定义。** 四个闭合片的 naive 拼接 HTML 与全量不同；附加同一组原始定义后相同。实验覆盖前向引用、首定义优先、重复定义晋升、大小写/空白规范化、多行目的地和标题；引用定义还可出现在引用容器内部。简单逐行正则提取不足以实现全局定义表。
- **[实测] 全局定义修改使依赖片失效。** 原型广播更新所有片的定义尾缀，5 MiB 约 99 ms，仍近似 O(n)。正式实现应建立 label → 使用片/块的依赖索引，定义新增时也需记录原先未解析成功的引用用户；脚注还有全局编号与导出排序。
- **[实测] 空行不是安全分割点。** 在围栏内部按空行切开得到不同结构；将定义追加到未闭合代码片末尾也会被吞成代码。合成定义后缀只证明闭合受限样例，不能原样扩展成通用分片算法。
- **[源码] [待验证] 顶层容器不保证小。** 一个长引用/列表/未闭合围栏可覆盖整个文档，parser.Edit 从顶层边界重新开始，这种文档仅按顶层块切片不能限定最坏成本。需要真正的 parser 引用上下文 API、状态检查点或明确的大文件降级；本 Spike 没有实现或测量完整通用分片器。
